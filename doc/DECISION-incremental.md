# 결정: 증분 분석

상태: **구현(미릴리스)** — 파일 단위 사실 캐시와 `--incremental <dir>`가
`lib/src/index/incremental_cache.dart`·`lib/src/index/analyzer_graph_index.dart`에
구현되어 색인 명령 11개에 배선됐다(브랜치 `feat/incremental-analysis`, 커밋
`00d22fa` 구현 + `941e595` 최적화). 다음 minor(0.10.0) 발행 후보이며
`doc/USAGE.md` 명령 목록에도 반영했다. 같은 P0의 **검증 원장(append-only JSONL)은
아직 미착수**다.

## 1. 문제

요구 4는 "CI에서 자동화할 만큼 빠르거나 증분"이다. 현재 분석은 매 실행마다 루트 안
전체 `.dart`를 다시 해석한다(캐시는 해석 결과가 아니라 실행 산출물 단위다). 대형
체크아웃에서 이 비용이 CI 상시 실행을 어렵게 만든다.

## 2. 결정

**파일 단위 사실 캐시 + 역방향 import 폐쇄 재해석**을 도입한다.

- 새 옵션: `--incremental <dir>`. 디렉터리는 호출자가 지정하고, 없으면 만든다.
- 캐시 단위는 **파일 하나**다. 키는 그 파일의 내용 해시 + 그 파일의 해석에 영향을 주는
  입력(설정·package config·의존 패키지 `lib`의 관련 해시·SDK 버전·도구 버전)이다.
- 실행 시:
  1. 대상 파일 집합과 각 파일의 현재 키를 계산한다.
  2. 키가 이전 실행과 같은 파일은 사실을 캐시에서 읽는다.
  3. 키가 달라진 파일 + 그 파일을 (전이적으로) import하는 파일만 다시 해석한다.
  4. 새 사실로 그래프를 재구성하고, 캐시를 원자적으로 갱신한다.

## 3. 이유

- 기존 `lib/src/index/`의 사실 추출 경로를 재사용할 수 있어 새 분석기를 만들지 않는다.
- import 폐쇄는 보수적이다. 즉 "다시 해석할 필요가 없는 파일"만 건너뛰고, 애매하면
  다시 해석한다. 놓치는 쪽보다 더 하는 쪽으로 기운다.
- 산출물은 전체 분석과 **byte 동등**해야 한다. 캐시는 속도만 바꾸고 출력은 바꾸지 않는다.

## 4. 무효화 규칙

| 입력이 바뀌면 | 무효화 범위 |
|---|---|
| 파일 내용 | 그 파일 + 역방향 import 폐쇄 |
| 루트 밖 상대 import 파일 | 그 파일을 import하는 파일(기존 캐시 키의 문서화된 경계를 계승) |
| `dartograph.yaml` `entry_points` | 보존 루트가 전역이라 **전체** |
| `pubspec.yaml`·package config·의존 패키지 `lib` | 관련 해석 입력이 바뀌므로 **전체** |
| 도구 버전 | **전체**(기존 `_cacheIdentity`와 같은 규칙) |
| SDK 버전 | **전체** |

## 5. 실패 경로

- **캐시 손상·버전 불일치**: 캐시를 무시하고 전체 분석으로 폴백한다. 오류로 끝내지
  않는다(캐시는 최적화지 계약이 아니다).
- **캐시 디렉터리 쓰기 실패**: 분석은 정상 수행하고, 캐시를 쓰지 못했다는 사실을
  limitation으로 남긴다.
- **분석 실패**: 기존 계약대로 종료 코드 2. 부분 결과로 오판을 유도하지 않는다.
- **중단(타임아웃·SIGINT)**: 임시 파일에 쓰고 rename으로 교체하므로 캐시가 반쯤
  갱신된 상태로 남지 않는다(`lib/src/core/atomic_write.dart`의 기존 경계를 재사용).

## 6. 완료 판정 기준

1. **출력 동등성**: 같은 입력에서 증분 실행과 전체 실행의 산출물이 byte 동일하다.
   `tool/benchmark_index.dart`의 7종 sha256 대조 방식을 그대로 쓴다.
2. **속도**: 동일 저장소·동일 입력에서 실측 배수를 기록한다. 목표는 전체 분석 대비 5배
   이상이고, 미달하면 실측값을 정직하게 적는다(측정 없는 최적화 금지 규칙).
3. **회귀**: 캐시 손상·버전 불일치·쓰기 실패·무효화 5종 각각에 단위 테스트가 있다.
4. **문서**: 구현 후 `doc/USAGE.md` 명령 목록과 `## 종료 코드`에 반영한다.
   (완료 — 명령 목록에 `--incremental <dir>`를 반영했다. 이 옵션은 종료 코드를 바꾸지
   않아 `## 종료 코드`에는 추가할 항목이 없다.)

## 7. 결정된 사항과 남은 미결

구현하면서 아래를 확정했다.

- **캐시 파일 형식**: 단일 JSON(`facts.json`), 압축 없음. 교체는 임시 파일 + rename
  (원자적)이라 중단돼도 이전 캐시가 남는다. 항목 하나가 손상되면 그 항목만 미스다.
- **폐쇄 경계**: import·export·part 지시문과 미해결(대상이 아직 없는) 지시문까지
  의존으로 센다. 조건부 import는 공개 analyzer가 고른 단일 구성만 보므로 기존
  `conditional-configuration` 한계를 따른다.
- **OS 캐시와의 관계**: 증분은 전체 결과 캐시를 읽지도 쓰지도 않는다. `--incremental`은
  호출자가 지정한 디렉터리에만 쓰고, 기존 OS 캐시 경로는 그대로 둔다.

남은 미결:

- 검증 원장(같은 P0 항목)과의 결합: 캐시 히트 여부를 원장에 남길지.

## 8. 되돌리기

`--incremental`은 옵션이므로 **주지 않으면 기존 경로 그대로**다. 문제가 생기면 플래그를
쓰지 않거나, 이후 릴리스에서 제거하면 된다. 캐시 디렉터리는 언제든 삭제해도 안전하다.

## 9. 구현 기록 (2026-09-15/16)

- **구현**: 커밋 `00d22fa`(Step A) + `941e595`(최적화). `--incremental <dir>`를
  색인 명령 11개가 받는다(help·USAGE 반영).
- **출력 동등성(§6-1)**: `tool/benchmark_index.dart`의 7종 산출물 sha256이 전체
  해석과 세 조건(변경 없음·널리 import되는 파일 변경·잎 파일 변경) 모두 일치한다.
- **속도(§6-2, 합성 600파일 실측)**: warm **7.5배**, leaf **1.9배**, imported

  목표 5배 미달을 그대로 기록한다.
- **회귀(§6-3)**: 캐시 손상·버전 불일치·쓰기 실패·삭제·part·설정 변경·의존 패키지

- **최적화(`941e595`)**: 파일 해싱 동기화, 캐시 사실 파싱을 폐쇄 계산 뒤로 지연,
  캐시가 현재 입력과 같으면 store 생략.
- **미착수**: 검증 원장(`--record` + `history`) — 같은 P0의 나머지 절반이다.

## 10. 사용자 캐시 모드와 캐시 파일 읽기 경계 (2026-10-20)

7절의 "`--incremental`은 호출자가 지정한 디렉터리에만 쓴다"는 그대로 유지한다. 이
기록은 그 위에 조건 두 가지를 더한다.

- **문제**: 훅(`setup --install`)·VS Code 확장·분석 서버 플러그인의 기본 인자와 예시
  워크플로가 분석 대상 안 디렉터리(`.dartograph/cache`, `.dartograph-facts`)를 썼다.
  캐시는 키가 맞는 사실을 다시 해석하지 않고 쓰는데 키는 공개 입력의 해시뿐이다. 그래서
  저장소가 위조한 `facts.json`을 커밋하면 결과가 바뀔 수 있었다. 또 `facts.json`을
  FIFO 링크로 두면 열기에서 영구 대기했다(실측: 훅과 같은 명령이 alarm 20초에서 rc 142).
  SECURITY.md의 "사실 캐시는 대상 밖 OS 사용자 캐시" 경계와 어긋났다.
- **결정 1 — 사용자 캐시 모드**: 값 없는 `--incremental-user-cache`를 더한다. 사실
  캐시를 `defaultAnalyzerCacheDirectory(canonical root)` 아래 `incremental/`에 둔다
  (`--workspace`는 `incremental-workspace/`). 통합 기본값은 이 모드로 옮긴다. 트리
  안 디렉터리는 명시한 `--incremental <dir>`로만 쓰고, 문서에 "신뢰하는 저장소 전용"으로
  적는다. 이 조건에서는 7절의 "기존 OS 캐시 경로는 그대로 둔다"가 바뀐다 — 증분은
  여전히 전체 결과 캐시 파일을 읽지도 쓰지도 않지만, 같은 루트별 디렉터리의 하위
  디렉터리를 쓴다.
  - 설계 결정 문서의 식은 `${XDG_CACHE_HOME:-$HOME/.cache}/dartograph/<sha 앞 16자>/`였다.
    이미 README 보장 절·SECURITY·index AGENTS에 문서화된 위치 계약(전체 sha256,
    macOS `~/Library/Caches`, Windows `%LOCALAPPDATA%`)을 따랐다. Linux 기준은 같고
    키 길이와 하위 디렉터리만 다르다. 프로젝트 하나의 캐시가 한곳에 모인다.
  - 디렉터리는 색인하는 canonical root마다 고른다. `compare`는 한 색인 함수로 두 루트를
    색인하므로 고정 디렉터리 하나를 쓰면 두 체크아웃이 서로 덮어쓴다.
  - 집계 여부로 나누는 이유는 MCP 세션 캐시와 같다(설정 지문이 달라 번갈아 덮어쓴다).
  - 사용자 캐시 위치를 정하지 못하면(HOME 등 부재) 캐시 없이 분석하고, 원인을 담은
    `incremental-cache-write-failed:` limitation을 남긴다. 결과는 완전하다.
  - 원장에는 스위치로 기록한다(`_ledgerSwitches`). 빠뜨리면 뒤따르는 패키지 루트를
    값으로 삼킨다.
- **결정 2 — 캐시 파일 읽기 경계**: `load`는 링크를 따라가지 않고 판정해 정규 파일만,
  1 GiB까지만 읽는다. 심볼릭 링크·FIFO·소켓이면 열지 않고 사실을 모두 다시 해석하며
  `incremental-cache-not-read:` limitation을 남긴다. 부재·디렉터리는 지금처럼 조용한
  미스다. 1 GiB는 리뷰 실측 최대 캐시(analyzer 코퍼스 1,568파일, 183.7 MB)의 다섯 배를
  넘는 폭주 방지선이다.
- **결정 3 — 예시 워크플로**: `.github/workflows/impact-precheck.yml`은 사실 캐시와
  원장을 체크아웃 밖 `runner.temp` 아래(`dartograph-facts`, `dartograph-ledger`)에 둔다.
  `actions/cache`는 이벤트 조건 없이 그 캐시를 복원·저장하고, 리포트·SARIF·게이트 단계가
  모두 같은 캐시를 쓴다. 전에는 PR 리포트 단계만 증분을 써서 SARIF·게이트 단계가 매번
  cold 전체 분석을 했다. 원장은 리포트와 따로 아티팩트로 올린다 — 한 아티팩트에 섞으면
  공통 조상이 아티팩트 루트가 되어 리포트 파일의 경로 모양이 바뀐다.
  - 사용자 캐시 모드를 쓰지 않은 이유: `actions/cache`의 `path`에 루트 해시를 넣어야 한다.
    러너가 정하는 임시 디렉터리를 명시하는 쪽이 복사해 쓰기 쉽다.
  - 실측(analyzer lib 코퍼스 447파일, `--changed`로 잎 파일 하나, 단계마다 빈 사용자 캐시,
    워밍업 뒤 다섯 번의 중앙값): SARIF 단계 5.74초 → 0.98초, 게이트 단계 5.75초 → 1.01초.
    두 단계의 출력 sha256은 cold 실행과 같다.
- **남은 것**: 캐시 항목의 무결성 표지(사용자 캐시에 둔 머신별 비밀로 HMAC)는 하지
  않았다. CI의 `actions/cache` 재사용을 깨므로 별도 결정이 필요하다. 트리 안 디렉터리의
  위조는 문서의 "신뢰하는 저장소 전용"으로만 막는다.

## 11. dup 전용 토큰 사실 분리 (2026-10-20)

7절의 "단일 JSON(`facts.json`)"은 이 기록부터 두 파일이다. 나머지 7절 결정은 그대로다.

- **문제**: 정규화 토큰 세그먼트는 `dup`만 쓴다. 그런데 사실 캐시 `facts.json`과 전체
  결과 캐시 항목에 함께 저장돼, 모든 색인 명령이 warm 실행마다 그것까지 읽고 디코드했다.
  analyzer lib 코퍼스(447파일)에서 `facts.json` 67.4 MB 중 20.4 MB(30%), 전체 결과 캐시
  항목 53.9 MB 중 20.5 MB(38%)가 토큰이었다.
- **결정 1 — 증분 캐시**: 토큰을 같은 디렉터리의 `tokens.json`에 둔다. 형식·스키마 버전·
  읽기 경계(10절 결정 2)·원자적 교체는 `facts.json`과 같고, 항목은 같은 파일 키로 검증한다.
  `dup`만 읽는다. `IncrementalCache.schemaVersion`은 2→3이다.
  - 다른 명령은 그 실행이 모든 파일을 해석했을 때만 `tokens.json`을 새로 쓴다. 재사용한
    파일의 토큰은 읽지 않았으므로, 일부만 쓰면 그 파일들의 토큰 항목을 잃는다.
  - 그래서 남은 낡은 항목은 다음 `dup`이 파일 키로 가려 그 파일만 다시 해석한다. 토큰은 그
    파일 내용만의 함수라 역방향 폐쇄로 넓히지 않는다. 지운 파일의 항목은 `dup`이 버린다.
  - 버린 `tokens.json`(링크·FIFO·소켓·상한 초과)은
    `incremental-cache-not-read: the dup token cache file …`로 남긴다. 사실 파일을 버린
    경우와 문구를 나눠 어느 파일인지 드러낸다.
- **결정 2 — 전체 결과 캐시**: 토큰을 결과 키에서 만든 별도 키의 항목에 둔다.
  `_cacheSchemaVersion`은 7→8이다. 추출 의미는 그대로라 `_cacheIdentity`는 올리지 않았다.
  - 분석한 실행은 명령과 무관하게 두 항목을 쓴다. 그래야 `dead` 뒤의 `dup`이 다시
    분석하지 않는다.
  - `dup`만 토큰 항목을 읽는다. 토큰 항목이 없거나 망가졌으면 결과 항목이 있어도 다시
    분석해 두 항목을 함께 복구한다.
- **결정 3 — 결과 계약**: `AnalyzerGraphIndex(includeTokenSegments: true)`인 색인만
  결과에 토큰을 싣는다. CLI는 `dup`만, MCP 세션은 `verify_run`의 `dup`만 이 값을 준다.
  해석하며 뽑은 토큰은 캐시에만 두고 다른 명령의 결과에서는 버린다. 캐시를 읽은 실행과
  해석한 실행의 결과가 같게 하려는 것이다.
- **하지 않은 것**: 토큰 코드를 고정 어휘표의 작은 정수로 직렬화하는 안은 설계 결정에
  따라 하지 않았다(dup의 창 해시 정렬 순서와 출력 동등성을 따로 검증해야 한다).
